# Cookie Factory

Cookie Factory provides repeatable project-generation wrappers for Cook's Code,
Inc. Development and verification run in containers so the host does not need a
project-specific Python virtual environment, Ruby installation, Jekyll, Node.js,
or linting tools.

## Development environment

The supported interactive environment is the VS Code Dev Containers extension.
It uses the `dev` service in `compose.yml` and installs the Python, ShellCheck,
YAML, and Codex extensions inside that environment.

1. Copy `.env.example` to `.env`.
2. Set `COOKIECUTTER_ROOT` to the absolute parent directory containing the
   template checkouts declared in `cookiecutters.yml`.
3. In VS Code, run **Dev Containers: Reopen in Container**.

The development container mounts Cookie Factory read/write and the complete
template root read-only at `/templates`. It does not mount the Docker socket,
host home directory, SSH keys, or cloud credentials.

## Verification

Build the toolchain once:

```shell
make build
```

Run the complete lint suite without runtime network access:

```shell
make lint
```

This checks Bash, Python, YAML, GitHub Actions, Dockerfiles, Markdown, spelling,
JSON, and repository formatting. Apply the supported automatic formatting with
`make format`; semantic lint findings still require a deliberate fix.

Run the pre-commit policy against every tracked file:

```shell
make pre-commit
```

The hooks reuse the pinned tools in the development image, run without network
access, and apply safe staged-file fixes for whitespace, line endings, Ruff, and
Prettier. Standard checks also cover syntax, merge markers, large files,
symlinks, executable permissions, debug statements, and private keys.

To enable automatic Git hooks, run this once from a terminal inside the VS Code
Dev Container:

```shell
pre-commit install --install-hooks
```

That installs both `pre-commit` and `pre-push` because the hook types are
declared in `.pre-commit-config.yaml` (the filename required by pre-commit). Run
commits from the same container; for
host-side commits, install pre-commit on the host or use `make pre-commit`.

Run deterministic tests without runtime network access:

```shell
make test
```

This runs Cookie Factory's tests, all 41 upstream bake tests from the five
enabled templates, a real GitHub Docs generation, and assertions over the
generated GitHub Pages routing and content. TypeScript remains cataloged but is
skipped with its structural failure recorded explicitly.

Run a real Jekyll remote-theme build when network verification is required:

```shell
make site-test
```

Run the complete CI-equivalent lint and test stages:

```shell
make verify
```

This rebuilds the current Dockerfile through the build cache before running the
same lint, test, and site-test services used by GitHub Actions, preventing a
stale local image from hiding a CI failure.

GitHub Actions uses the same image and Compose services, so local and CI
verification share one contract. Pre-commit remains a local developer aid; CI
validates the same relevant policies through the independent `lint` service
without invoking the `hooks` service.

## Development, CI, and releases

The repository deliberately separates the three workflows:

```text
VS Code Dev Container
        |
        v
 Local Pre-Commit
        |
        v
    Git Commit
        |
        v
     Git Push
        |
        v
  GitHub Actions
        |
        +-- Docker Lint
        |
        +-- Docker Tests
        |
        +-- Jekyll Build
        |
        v
 Merge into master
        |
        v
 Create Version Tag
        |
        v
 Release Validation
        |
        v
 Generate Release Notes
        |
        v
  GitHub Release
```

Ordinary branch pushes and pull requests can run container verification, but
they cannot publish a release. Only a manually created semantic version tag on
a commit reachable from `master` starts the release workflow.

## Preparing a release

Cookie Factory's version is stored in `VERSION` and follows `MAJOR.MINOR.PATCH`
semantic versioning. This is independent of the default version assigned to a
project generated by a Cookiecutter template; preparing a Cookie Factory
release must not change generated-project versions.

1. Choose the next version: increment MAJOR for incompatible changes, MINOR for
   backward-compatible features, or PATCH for backward-compatible fixes.
2. Update `VERSION` in the release-preparation change, complete review, and
   merge it into `master`. The clean `master` checkout must contain the exact
   version that will be tagged.
3. Build the pinned toolchain and validate the candidate:

   ```shell
   make build
   make verify
   make release-check
   make release-notes
   make release-dry-run
   ```

4. Inspect `build/release-notes.md`. The notes are generated from the commits
   after the previous reachable semantic version tag through the exact release
   commit. The dry run neither creates a tag nor contacts the release-publishing
   API.
5. Create and push an annotated tag only after approval, using the commands
   printed by `make release-dry-run`:

   ```shell
   git tag --annotate v0.1.0 --message "Release v0.1.0"
   git push origin v0.1.0
   ```

6. Monitor **Publish GitHub Release** in GitHub Actions. It validates the tag,
   confirms the commit is reachable from `master`, rejects duplicate releases,
   reruns the container workflow, regenerates the notes, and publishes with
   `gh release create --verify-tag` only after all checks pass.
7. Confirm the entry and notes on the repository's **Releases** page.

`make release` is a safeguarded alias for the local dry run and instructions;
it never creates or pushes a tag and never publishes a release. Prereleases are
disabled by default. Maintainers must deliberately enable the repository
variable `RELEASE_ALLOW_PRERELEASE=true` and use
`ALLOW_PRERELEASE=true make release-dry-run` for a tag such as `v1.0.0-rc.1`.

Treat published tags and releases as immutable. If a workflow fails, diagnose
the failed validation without moving or force-pushing the tag. Put any required
fix in a new reviewed `master` commit, choose a new semantic version, and create
a new tag. Never overwrite or reuse a published version.

Recommended GitHub rulesets protect `master` with pull requests and the
required **Container tests / verify** check. Protect tags matching `v*` by
restricting creation to maintainers and blocking updates and deletion. Protect
the `github-release` environment with the desired reviewer approval. Release
tooling uses GitHub's repository context, so moving the repository to an
organization does not require a hardcoded owner change.

GitHub Releases and GitHub Pages are separate outputs. A Release is an immutable
version record created from an approved tag; this repository has no meaningful
binary artifact, so GitHub's source archives are sufficient. GitHub Pages is
the continuously published Jekyll documentation site and does not establish a
software version or release.

## Template catalog and generation

`cookiecutters.yml` is the canonical inventory. It records each local directory,
GitHub repository, tested ref, enablement state, and upstream test interface.
Validate the catalog and its read-only local checkouts with:

```shell
make templates-list
make templates-validate
```

Generate an enabled template with its defaults into `build/generated`:

```shell
make generate TEMPLATE=python3
```

Use the generic wrapper for context overrides:

```shell
./cookie-factory.sh generate python3 \
  --set project_name=example_project \
  --set license=GPL-3.0-or-later
```

Available enabled IDs are `ansible-galaxy`, `cookiecutter`, `github-docs`,
`python3`, and `sphinx`. The `typescript` entry is intentionally disabled
because that repository does not yet contain a templated project directory.
Attempting to generate a disabled entry fails with the recorded reason.

Cookie Factory never writes to template repositories. Compose mounts the
entire template root read-only, while generated projects go to `build/` or a
caller-selected output directory.

## GitHub Docs generation

The host-friendly defaults still work when the Nutri-Matic virtual environment
is present:

```shell
./github-docs-cookie.sh
```

Container and CI callers override paths without modifying the script:

```shell
CI=1 \
COOKIE_REPO=/templates/github-doc-cookiecutter \
BRANCH= \
PYTHON_ACTIVATE= \
OUTPUT_DIR=/output \
./github-docs-cookie.sh
```

The representative build generates Cookie Factory documentation using the
pinned Just the Docs theme and GitHub Project Pages routing. Regenerate the
checked-in site from the mounted `github-docs-cookiecutter` checkout with:

```shell
make docs-generate
```

The generated source is installed at `docs/jekyll`. Review the resulting diff
before committing an upstream template update. The published site is available
at [jcook3701.github.io/cookie-factory](https://jcook3701.github.io/cookie-factory).

## Legacy generator entry points

The older `cookie-cookie.sh`, `ansible-galaxy-cookie.sh`, `python-3-cookie.sh`,
and `template-generator.sh` scripts remain for compatibility. New automation
should use `cookie-factory.sh` and the catalog IDs so every template shares the
same container and validation path.

## Kubernetes

Kubernetes is intentionally not part of the default workflow. This repository
does not deploy a Kubernetes workload, so Compose is the smaller and more
reproducible execution boundary. If a generated project later ships Kubernetes
manifests, add an optional `kind` end-to-end stage without replacing the fast
Compose test path.
